# 电商接入 ANET ERP（SAP 风格系统）：差距与清单（2026-11-24）

对象系统：`C:\Users\maxinjian\Desktop\AI\AI_ScanCAD\japan-erp`（http://127.0.0.1:8090/，版本 0.5）。
本文只是读代码和文档后的分析，**没有改动该项目任何文件**。

## 一、先说结论

- 这个 ERP 现在是「批发/贸易公司」的形状：受注 → 承认 → 引当 → 出荷 → 请款 → 入金，采购 → 检收 → 请款 → 付款，邮件转业务，AI 评测。销售、采购、库存、辅助会计都有事务和审计，底子比电商仓库（jianpanerp）里的订单模块扎实。
- 它完全没有电商的概念：没有「渠道」、没有「渠道 SKU 对照」、没有规格（颜色/尺码）、没有个人买家订单、没有平台费/运费/广告费、没有退货。
- 电商这边（jianpanerp）正相反：各平台的操作都跑通了，但订单、库存、利润散在各平台后台和脚本输出里，没有一处能看到「每个商品在每个店卖了多少、赚了多少、还剩多少」。
- 所以接入的方向是：**ERP 做唯一的商品、库存、订单、利润账本；各平台做成连接器，把订单读进来、把库存和价格写出去。** 这正好是 ERP 文档里写的规则（「连接器禁止直接改库存表，必须走业务服务」）。
- 需要您知道的两点冲突：
  1. ERP 的 README 写明「没有导入电商项目的源码和数据库」。接入应当用连接器和数据导入，不是把 jianpanerp 的代码搬过去。
  2. 10-29 您定的方针是「卖货优先、不建新系统」。这次接入算建系统。建议每一步都选「直接帮到卖货」的先做（见第五节）。

## 二、ERP 现状（代码核对）

| 项目 | 现状 |
|---|---|
| 技术 | FastAPI + PostgreSQL 17（强制租户隔离）+ React / SAP 官方开源 UI5 控件，Docker 6 个容器在运行 |
| 数据表 | 约 40 张：客户、商品、受注、交货、请款、入金、库存流水、会计凭证、供应商、采购、检收、供应商请款、付款、邮件、任务、资料库、AI 评测 |
| 商品 | 只有 编号、名称、单位、售价、标准原价、税率、在库、引当、补货点。**没有规格、图片、JAN、渠道信息** |
| 库存 | 一个企业一个库存池。没有多仓库（自家仓 / FBA / 批发商代发分不开） |
| 订单 | 面向企业客户（客户主数据 + 承认流程）。没有运费、手续费、积分、优惠券字段 |
| 对外 | 只绑定 127.0.0.1；Gmail 连接器已写好但未授权；没有任何电商平台连接器 |
| 未实现（README 自述） | 退货/贷项、多仓库、批次、多币种、完整总账、正式适格請求書、银行对账、自动备份 |

## 三、电商这边已有、可以喂给 ERP 的东西

| 渠道 | 现在怎么操作的 | 能给 ERP 什么 |
|---|---|---|
| 乐天 | RMS API 直接可用（商品、库存、价格、图片、非表示开关都在用） | 商品与规格、库存、价格；订单接口要先试一次才能确认 |
| Shopify | API 可用（商品、订单、发货权限；**没有库存权限**） | 商品、订单；库存写回要先给应用加权限 |
| Amazon | **SP-API 凭据已失效**（11-12 实测），现在靠 Seller Central 表格上传和下载报告 | 报告文件（订单、ビジネスレポート、FBA 在库）可以导入；自动同步不行 |
| Qoo10 | QSM 一括登録 Excel，店铺还在审查，库存与乐天不联动 | Excel 导入导出 |
| Yahoo! | 仓库里没有任何 Yahoo 的代码和数据 | 目前没有 |
| 批发商 / 1688 | 批发商站采集（进价、在售状态）、1688 找款记录 | 进价 → ERP 的标准原价；进货 → ERP 采购单 |
| 其他 | 6kpro 模型网关、商品图/文案流水线、IG 发帖、品牌洽谈邮件 | 文案评测可用 ERP 的「AI評価」；洽谈邮件可进 ERP 的邮件中心 |

## 四、对比强的电商卖家，不足在哪

这一节的「强卖家」指多渠道做到年销数亿日元以上的品牌卖家，以及日本常用的一元管理工具（ネクストエンジン、クロスモール等）已提供的能力。**依据是我对这些公司和工具公开做法的了解，没有做专门调研，也没有他们的内部数据。**

| # | 强卖家的做法 | 我们现在 | 属于 |
|---|---|---|---|
| 1 | 所有渠道的库存一处管理，卖一件各店同时减 | 各店各管各的，Qoo10 与乐天不联动，靠人工 | 系统 |
| 2 | 每个 SKU 每个渠道的净利润每天可见（售价−进价−平台费−运费−广告） | 只有估算倍率（进价 ×1.35 等），没有按单核算 | 系统 |
| 3 | 订单自动汇总、自动出送り状、当天出货 | 代发 1〜2 天，FBA 的 SALONCARE 新链接库存全是 0 | 系统 + 运营 |
| 4 | 广告按检索词每周调整，ACOS 有目标 | 乐天 RPP、Amazon 广告的报告都还没拿到，没有闭环 | 运营 |
| 5 | 销售分散在多个主力商品 | 乐天 89% 靠一个商品；Amazon 集中在内衣家居 7 个系列 | 经营 |
| 6 | 自有品牌，评价数量多，有复购 | BANZ 是代理；SALONCARE 刚换牌，新链接评价为零 | 经营 |
| 7 | 新品从选品到上架有固定流程和数据依据 | 有 SOP（选品 13 步、画像 SOP），但没有一次完整跑到出单 | 运营 |
| 8 | 按销量预测自动提示补货 | 没有；销量数据也太少 | 系统 |
| 9 | 客服集中处理，有模板和时限 | 各平台后台分别处理 | 系统 |
| 10 | 退货、差评有记录并回到商品改进 | 没有记录 | 系统 |
| 11 | 会员、LINE、邮件做复购 | 没有 | 运营 |
| 12 | 会计、适格請求書、对账自动化 | ERP 只有辅助账，自述未经税理士验收 | 系统 + 专家 |

要点：第 5、6 项系统解决不了。系统能解决的是 1、2、3、8、9、10。

## 七、两个项目怎么分工

- **japan-erp**：账本。商品、库存、订单、采购、利润、邮件任务。新增一个「渠道连接器」层，结构参照已有的 Gmail 连接器（只读同步、受限数据库角色、人工确认后才生成业务单据）。
- **jianpanerp**：各平台的手脚。上架、改图、文案、发帖、浏览器操作继续留在这里；产出的数据（SKU、价格、库存、订单文件）按固定格式交给 ERP。
- 那边目前另有一个会话在开发（今天部署了批量导入）。两个会话不要同时改同一批文件。
