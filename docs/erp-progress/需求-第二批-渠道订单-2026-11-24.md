# ANET ERP 电商接入 第二批需求：渠道订单 → 销售额、费用、利润（2026-11-24）

提出：电商会话。实现：ERP 会话。文件版本 v2.0（草案，等 ERP 会话回复后定稿）。
目的只有一个：让用户每天打开 ERP 就能看到「昨天各店卖了什么、卖了多少钱、扣掉进价和费用后赚多少」，并且自家仓库存随出货减少。

## 0. 原则

1. **金额以渠道给的含税金额为准**，ERP 不从税抜单价回算。税抜金额按「订单行的含税金额」整体换算一次（税额 = 含税 × 税率 ÷ (100 + 税率)，舍去小数）。
2. **不导入买家个人信息**：文件里没有姓名、地址、电话、邮箱；只有都道府县（算运费用）。ERP 里每个渠道用一个固定的受注先（例「楽天市場店 購入者」）。
3. **进价未登録的 SKU，利润显示「未計算」**，不当作 0 円成本算出虚高利润；合计旁注明有几行未计算。
4. **可重复读入**：同一订单再读一次只更新状态，不重复计数。
5. 估算值和实际值分开标记，页面上看得出哪个是估算。

## 1. 文件 ⑤ 订单明细 `orders.csv`（一行 = 一个订单的一条明细）

唯一键：(`channel_code`, `order_no`, `line_no`)。

| 列 | 必填 | 规则 |
|---|---|---|
| `channel_code` | 是 | 已登记的渠道编号 |
| `order_no` | 是 | 渠道的订单号，原样 |
| `line_no` | 是 | 订单内的明细序号，1 起。渠道没有序号时由电商会话按导出顺序编 |
| `order_date` | 是 | 下单时间，`YYYY-MM-DD HH:MM`，日本时间 |
| `status` | 是 | `ordered`（已下单未出货）/ `shipped`（已出货）/ `cancelled`（整行取消） |
| `shipped_date` | 否 | 出货日，`status=shipped` 时必填 |
| `parent_key` | 是 | 与渠道对照文件 ② 相同的主标识 |
| `listing_key` | 是 | 与渠道对照文件 ② 相同的子标识。用 (`channel_code`, `parent_key`, `listing_key`) 找到 SKU |
| `item_name` | 否 | 渠道上的商品名，只用于对不上时给人看 |
| `quantity` | 是 | 卖出件数（渠道上的件数；消耗库存 = quantity × 对照的 `units`） |
| `line_amount_tax_included` | 是 | 这一行的含税金额 = 渠道售价 × 件数 − 店铺承担的商品级折扣 |
| `tax_rate` | 否 | 默认 10 |
| `shipping_charged_tax_included` | 否 | 买家支付的运费（含税）。只写在该订单的第 1 行，其余行留空 |
| `shop_discount_tax_included` | 否 | 店铺承担的订单级优惠（店铺券等）。只写在第 1 行 |
| `platform_discount_tax_included` | 否 | 平台承担的优惠和买家使用的积分。**不减少店铺收入**，只作记录。只写在第 1 行 |
| `fulfillment` | 否 | `own` / `fba` / `dropship`。留空用对照里的值 |
| `prefecture` | 否 | 收货都道府县 |
| `returned_quantity` | 否 | 已退货件数，默认 0 |
| `refund_tax_included` | 否 | 已退款金额（含税），默认 0 |
| `return_date` | 否 | 退货受理日 |

店铺收入（含税）= Σ`line_amount_tax_included` + `shipping_charged_tax_included` − `shop_discount_tax_included` − `refund_tax_included`。

### 读入时的检查
- 对不上对照的行（`parent_key`/`listing_key` 在 ② 里不存在）：整份不拒绝，列在「未紐付け」清单里并给出件数，这些行不计入库存和利润，补了对照后重读即可归位。
- 同一订单内第 1 行以外写了订单级金额：报错。
- `status=cancelled` 的行：不计销售额、不减库存。部分取消用减少 `quantity` 表示。
- 已存在的订单再次读入：比较后只更新有变化的字段，报告「新增 / 更新 / 没有变化」件数。

### 库存
- 每个库存地点有一个「期初日」（自家仓 = 2026-11-24）。**期初日当天及以后出货**的 `own` 订单才减自家仓库存（按 `shipped_date`）；更早的订单只进销售和利润统计，不动库存。
- `fba`、`dropship` 的订单不动自家仓库存。
- 退货：`returned_quantity` 不自动加回库存（退回品能不能再卖要人判断），在商品页显示「返品 N 件」。

## 2. 文件 ⑥ 订单费用 `order_fees.csv`（一行 = 一个订单的一笔费用）

费用在结算报告里才有，晚于订单，所以单独一个文件。

| 列 | 必填 | 规则 |
|---|---|---|
| `channel_code` | 是 | |
| `order_no` | 是 | |
| `fee_type` | 是 | `commission`（销售手续费）/ `payment`（决济手续费）/ `points`（店铺承担的积分）/ `fba`（FBA 配送代行费）/ `shipping`（店铺付给快递的运费）/ `dropship_shipping`（代发方收的运费）/ `other` |
| `amount_tax_included` | 是 | 含税金额，正数 = 店铺支出 |
| `basis` | 是 | `actual`（来自结算或账单）/ `estimate`（估算） |
| `note` | 否 | 出处，例「楽天 請求明細 2026-11」 |

同一 (`channel_code`, `order_no`, `fee_type`) 再读入时覆盖；`actual` 覆盖 `estimate`，反过来不覆盖。

### 没有实际费用时的估算
渠道主数据上加两项，订单没有 `actual` 费用时按它估算并标「見込み」：
- 销售手续费率（%）：对店铺收入（含税）计算。
- 每单运费（円）：`own` 订单用；`dropship` 订单的运费由电商会话在 ⑥ 里给。

初始值由用户定（乐天约 10% 是此前的估算，Amazon 按类目不同，未确认）。

## 3. 页面

1. **首页**：昨天 / 本月的「受注件数、売上（税込）、粗利」，按渠道分。
2. **受注一览**：能按渠道、状态、期间筛选；渠道订单号能检索；来源显示「取込」。
3. **商品页**加「販売実績」：按渠道显示近 30 天销量、売上、粗利、粗利率、返品件数。
4. **利润一览**（新页面）：行 = 商品 × 渠道，列 = 销量、売上（税抜）、原価、手数料、送料、粗利、粗利率；可按期间筛选、按粗利排序；估算费用带「見込み」标记；进价未登録的行显示「未計算」。
5. 「未紐付け」清单：对不上的订单行，显示渠道、订单号、`parent_key`、`listing_key`、商品名。

粗利 = 売上（税抜）− 原価（税抜）× 消耗件数 − 费用（税抜）。费用按订单内各行的含税金额比例分摊到行。

## 5. 验收标准（电商会话在 `trial` 里核对）

1. 乐天 2026-09-12〜11-12 的订单读入后，件数与売上合计和 RMS 的数字一致（此前统计：174 单、¥755,801，以出文件时重取的数字为准）。
2. 同一文件读两次，第二次全部「没有变化」，合计不变。
3. 含税 3,600 円（1,800 × 2）的订单行在 ERP 里仍是含税 3,600，不是 3,601。
4. 取消的订单不计入売上；部分退款的订单売上减少退款额。
5. 期初日以后出货的自家仓订单，库存按 quantity × units 减少；期初日以前的不减。
6. 进价未登録的商品，利润显示「未計算」，合计旁有未计算行数。
7. 把一条对照删掉再读入，对应订单行出现在「未紐付け」清单；补回对照后重读，清单消失。
8. 文件里没有任何买家姓名、地址、电话、邮箱。

## 6. 这一批不做（第三批）

渠道显示库存与 ERP 库存的差异对比、广告费分摊、结算入金对账、退货品再入库流程。

## 7. 请 ERP 会话回答

1. 渠道订单在 ERP 里是进现有的「受注」模型，还是单独的渠道订单表？如果进受注，出货、请求、入金是否自动生成，会不会把首页的「未転記の出荷伝票」「未回収残高」撑大。
2. 库存地点的「期初日」现在有没有这个概念；没有的话打算怎么避免 11-24 以前的订单重复扣库存。
3. 费用按含税金额比例分摊到行，有没有更合适的现成做法。
4. 两份文件的列有没有与现有导入框架冲突的地方；列名可以按你的习惯改，改完告诉我。
